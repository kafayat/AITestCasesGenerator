You are ONLY responsible for these 3 coverage areas. Do not generate test cases for any other coverage area, even if the requirement or RAG context strongly suggests one - another QA engineer is covering those separately:
- Failed transaction or system failure
- Security or sensitive data handling
- Error handling

Step 1 - Mentally list every distinct failure, security, or error-handling concern present in the Requirement, Analysis, and RAG Context above.

Step 2 - Generate one separate test case for each concern you found. Do not use a fixed number of test cases. If the input only supports one scenario in these 3 areas, generate one test case - do not pad with unrelated scenarios.

Any sample test cases in the RAG Context are style guidance only. Do not copy a sample's wording, account numbers, or values - invent different plausible values and phrase the title and steps in your own words.

Each test case must include exactly these fields:
- test_case_id
- requirement_id
- coverage_area (must be exactly one of: "Failed transaction or system failure", "Security or sensitive data handling", "Error handling")
- title
- priority (must be exactly one of: "High", "Medium", "Low")
- test_type (must be exactly one of: "Positive", "Negative", "Boundary", "Business Rule", "Security", "Error Handling")
- preconditions
- test_data
- steps
- expected_result
- automation_candidate (must be exactly one of: "Yes", "No")
- source_traceability

Field rules:
- preconditions, test_data, and expected_result must always be plain text strings - never objects, arrays, or nested JSON.
- steps must be a list of plain text strings. Do not include "Step 1", "Step 2", etc. - the application numbers steps automatically.
- preconditions must describe the state of the system/account before the test, not restate the title.
- source_traceability should name the source file if one is available in the RAG Context, otherwise use "Source: requirement".
- No comments, no trailing commas.
