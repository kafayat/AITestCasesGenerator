Step 1 - Before writing any JSON, mentally list every distinct behaviour, business rule, validation, and acceptance criterion present in the Requirement, Analysis, and RAG Context above.

Step 2 - For each coverage area below, generate one separate test case ONLY if something in the input actually relates to it. Skip an area only if nothing in the input supports it. Do not invent behaviour that isn't implied by the input.

Coverage areas:
- Happy path / successful flow
- Invalid input
- Missing mandatory data
- Business rule validation
- Boundary condition
- Duplicate processing
- Failed transaction or system failure
- Confirmation or notification
- Receipt or reference generation
- Security or sensitive data handling
- Data integrity
- Error handling

Do not use a fixed number of test cases. Do not generate only one test case when the input contains multiple behaviours. Coverage is more important than quantity. Use sample test cases only as style guidance — do not copy them verbatim, and do not base every test case on only one sample.

Each test case must include exactly these fields:
- test_case_id
- requirement_id
- coverage_area (must be one of the 12 coverage areas listed above, written exactly as shown)
- title
- priority (must be exactly one of: "High", "Medium", "Low")
- test_type (must be exactly one of: "Positive", "Negative", "Boundary", "Business Rule", "Security", "Error Handling")
- preconditions
- test_data
- steps
- expected_result
- automation_candidate (must be exactly one of: "Yes", "No")
- source_traceability

Field rules:
- preconditions, test_data, and expected_result must always be plain text strings — never objects, arrays, or nested JSON.
- steps must be a list of plain text strings. Do not include "Step 1", "Step 2", etc. — the application numbers steps automatically.
- source_traceability should name the source file if one is available in the RAG Context, otherwise use "Source: requirement".
- No comments, no trailing commas.
