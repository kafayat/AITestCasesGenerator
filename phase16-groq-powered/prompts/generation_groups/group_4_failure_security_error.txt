You are ONLY responsible for these 3 coverage areas:
- Failed transaction or system failure
- Security or sensitive data handling
- Error handling

Step 1 - Read the Requirement carefully. List every distinct failure scenario, every security or access control concern, and every error handling requirement. Count them.

Step 2 - Generate ONE separate test case for EACH distinct scenario you found.

MINIMUM EXPECTATION: Generate at least 2 test cases. At minimum one for error handling (what happens when something goes wrong during submission) and one for security (who can access this form/feature and what happens if an unauthorised user tries). If the requirement explicitly names "Security and access control" as a required coverage area, you MUST generate a security test case even if no detailed security use case is described - infer it from the actors/roles listed in the requirement.

IMPORTANT - the worked example below is from a COMPLETELY DIFFERENT, UNRELATED business domain. Copy its JSON structure only, never its wording or domain content.

Each test case must include exactly these fields:
- test_case_id
- requirement_id
- coverage_area (must be exactly one of: "Failed transaction or system failure", "Security or sensitive data handling", "Error handling")
- title
- priority (must be exactly one of: "High", "Medium", "Low")
- test_type (must be exactly one of: "Positive", "Negative", "Boundary", "Business Rule", "Security", "Error Handling")
- preconditions
- test_data
- steps
- expected_result
- automation_candidate (must be exactly one of: "Yes", "No")
- source_traceability

Field rules:
- preconditions, test_data, and expected_result must always be plain text strings - never objects, arrays, or nested JSON, and never left empty.
- steps must be a list of at least 3 plain text strings. Do not include "Step 1", "Step 2" etc.
- source_traceability must never be left empty. Default: "Source: requirement".
- No comments, no trailing commas.
